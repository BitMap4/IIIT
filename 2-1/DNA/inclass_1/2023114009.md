

2. One INSERT that violates key constraint
```sql
INSERT INTO EMPLOYEE (Fname, Minit, Lname, Ssn, Bdate, Address, Sex, Salary, Super_ssn, Dno)
VALUES ('John', 'B', 'Doe', 123456789, '1965-01-09', '731 Fondren, Houston, TX', 'M', 30000, 333445555, 5);
```
This violates key constraints because John Smith already has that `Ssn`


3. One INSERT that violates referential integrity constraints
```sql
INSERT INTO EMPLOYEE (Fname, Minit, Lname, Ssn, Bdate, Address, Sex, Salary, Super_ssn, Dno)
VALUES ('Yefri', 'M', 'Reyes', 987654321, '1992-03-21', '456 Elm St, Dallas, TX', 'F', 48000, 333445555, 10);
```
This violates referential integrity constraints because `Dno` is 10 but no department exists in the table with `Dnumber`=10


4. One DELETE on EMPLOYEE that is acceptable
```sql
DELETE FROM EMPLOYEE WHERE Ssn = 555555555;
```
Valid because this `Ssn` is not referenced anywhere else, as we just added this entry in (1) so referential integrity remains intact. 
*Note*: if we are supposed to perform these actions by assuming the given state of the database (and not the current state, after performing the above actions), **then no acceptable DELETE is possible**, as the `WORKS_ON` table references all employees' `Ssn`s as foreign keys in the `Essn` column


5. One DELETE on EMPLOYEE that violates referential integrity constraints
```sql
DELETE FROM EMPLOYEE WHERE Ssn = 333445555;
```
Violates because this `Ssn` is referenced several times in the database, like in the `Super_ssn` of John Smith.

7. One UPDATE on EMPLOYEE that violates referential integrity constraints

*Note*: If we must perform a DELETE, and aren't allowed to use an acceptable DELETE statement that doesn't actually delete a row, **then no acceptable DELETE is possible on PROJECT**, as all rows have `Pnumber` that is referenced in the WORKS_ON table.
